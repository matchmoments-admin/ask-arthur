## Rating definitions

Scores are ordinal **1–5**, higher is better. Do not average security into a business score: a serious security gap can block launch regardless of usefulness.

| Score | Usefulness: current strategic contribution    | Security: assurance from this initial review                                                | Completion: delivery readiness                                                             |
| ----- | --------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 1     | Parked/no current case                        | Material visible protection gap or missing foundation                                       | Scaffold/plan                                                                              |
| 2     | Conditional/low present priority              | Significant gaps or very limited implemented assurance                                      | Partial or blocked delivery                                                                |
| 3     | Helpful supporting feature                    | Controls visible; important paths unverified                                                | Substantial implementation; integration/activation proof outstanding                       |
| 4     | Strong mission/revenue contribution           | Relevant controls inspected and focused regression tests passed; wider audit still required | End-to-end implementation appears substantially present; production acceptance outstanding |
| 5     | Core mission, funding or essential dependency | Comprehensive adversarial and deployed-state validation                                     | Activated, monitored and evidenced user outcomes                                           |

Usefulness is a reasoned judgment against [the project’s stated strategy](/Users/brendanmilton/Desktop/projects/safeverify/NORTH_STAR.md), not measured demand. Security scores rate available assurance, not exploit probability; a 3 is provisional, not “safe.” Completion is not percentage of lines written. No feature receives security/completion 5 because deployed-state and user-outcome evidence were not collected. “Built” means present in this checkout; “gated” means an enabling path exists in code, not that the production flag is OFF or ON. Family-level scores take material shared gaps into account; a later deep review should split any family whose subfeatures materially diverge.

## Initial findings to verify or address first

These are source findings, not proof of production exploitation. Severity below is conditional on reachability/configuration. No issue numbers were created and no existing issue state was inferred from GitHub.

1. **High priority before audio-deepfake activation: unmetered external calls.** [apps/web/app/api/deepfake/route.ts:9](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/app/api/deepfake/route.ts:9) goes from a feature gate and file checks to the provider helper without a rate-limit check. [packages/scam-engine/src/deepfake-detect.ts:13](/Users/brendanmilton/Desktop/projects/safeverify/packages/scam-engine/src/deepfake-detect.ts:13) contains external fetches but no request timeout, cost logging or feature-brake read. Middleware inspection did not show an equivalent per-feature control. With the feature and provider key enabled, repeated uploads can repeatedly call the provider. Add bounded execution, an enforced rate/spend limit and metering; verify repeated requests stop reaching a mocked provider and provider stalls terminate. External infrastructure might add protection, but none was verified.
2. **High priority for result integrity: provider unavailability resembles a negative finding.** [packages/scam-engine/src/deepfake-detect.ts:41](/Users/brendanmilton/Desktop/projects/safeverify/packages/scam-engine/src/deepfake-detect.ts:41) returns `isDeepfake: false`, confidence 0 and provider `none` when no provider works; [apps/web/app/api/deepfake/route.ts:55](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/app/api/deepfake/route.ts:55) returns this as a successful response and omits the helper’s error details. Consumers receive an availability hint in `provider`, but no explicit unavailable/error status. Require a distinct unavailable result and prove the UI never interprets it as an authentic recording. Test missing credentials, both providers failing and malformed provider responses.
3. **High priority before Phone Footprint fleet revival: incomplete ownership enforcement.** [apps/web/app/api/stripe/webhook/route.ts:349](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/app/api/stripe/webhook/route.ts:349) derives fleet `orgId` from subscription metadata but only checks customer ownership for non-fleet entitlements. This matches the documented accepted risk in NORTH_STAR/backlog. The missing check is confirmed; arbitrary attacker control of Stripe metadata was not demonstrated. Review the complete checkout-to-webhook chain and require a server-derived, authorised customer/org association before provisioning. Test another org’s identifier and changed membership. Keep the feature parked under its existing decision.
4. **Medium priority before media scale-up: non-atomic work claim.** [apps/web/app/api/media/analyze/route.ts:29](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/app/api/media/analyze/route.ts:29) reads `pending` and later starts work. [apps/web/lib/mediaAnalysis.ts:99](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/lib/mediaAnalysis.ts:99) updates by job ID without a current-status predicate, and `:126–133` proceeds to download/transcribe. Two simultaneous requests can both observe pending and run paid work. This is a source-level race, not a concurrency reproduction from this session. Add an atomic pending-to-processing claim or equivalent lock and a barrier-based test asserting one transcription and one analysis. Separately decide/document whether job UUIDs are bearer capabilities; verify retention and result access against that contract.
5. **Review-planning defect: historical documentation is not a current issue queue.** BACKLOG still repeats the rejected-UNCERTAIN and cache-skips-persistence findings, while [supabase/migration-v268-uncertain-verdict.sql:28](/Users/brendanmilton/Desktop/projects/safeverify/supabase/migration-v268-uncertain-verdict.sql:28) includes UNCERTAIN and [apps/web/app/api/analyze/route.ts:223](/Users/brendanmilton/Desktop/projects/safeverify/apps/web/app/api/analyze/route.ts:223) emits a cache-hit event when the Inngest flag is on. The remaining question is deployed migration/flag state and the legacy flag-off behaviour, not “implement the missing fix.” Likewise the current RPC smoke suite has more cases than the old 13-RPC description, but still skips real SQL when credentials are absent. Reconcile documentation against enforcing code and dated environment evidence before re-filing work.

## Finding template and closure rules

Record: feature ID; severity and activation condition; pinned commit/environment; source lines; reproducible trigger; expected versus actual result; user/security impact; confidence; proposed correction; regression test; owner; acceptance evidence. Separate **confirmed source defect**, **reproduced defect**, **documented accepted risk**, **production-state unknown** and **review question**.

Fixes close only after the regression fails before the change, passes afterwards, and affected integration checks pass. Availability/security blockers are checked again at activation. Product usefulness is revisited after measured demand, not increased merely because more code shipped. Refresh this catalogue after the deep review and after any material activation or product-direction change.
