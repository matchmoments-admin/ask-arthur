## 2. The one new defect — PR #896 (open)

`🚨 Threat feed scraper failed` has been paging **every 3 hours** since
2026-08-03. It is `acsc_alerts`, and it is **not** a regression in any single PR:

- **#879** added the failure gate (correct — it is why this is visible)
- **#880** un-latched the backoff, so `acsc_alerts` now genuinely attempts
  every run instead of skipping (correct)
- **v264** muted `acsc` with an expiry (correct)

**The gap:** `feed_sources.muted_until` is the single source of truth for
"knowingly broken, do not alarm", and **only `health-digest` honoured it**. The
GitHub Actions pager never knew it existed. Muting a feed silenced one alerting
path and not the other.

PR #896 makes the pager mute-aware. Two details worth knowing before reviewing:

- It resolves module→slug by importing each scraper's `FEED_NAME` rather than
  using a hand-written map. Four of eighteen differ (`acsc_alerts`→`acsc`,
  `scamwatch_alerts`→`scamwatch_alert`, `asic_investor_alerts`→`asic_investor`,
  `reddit_scams`→`reddit`). A map here would be a second registry that drifts —
  exactly what v264 deleted with `KNOWN_DORMANT_FEEDS`.
- **Suppression requires a positive match.** Unresolvable module, missing roster
  row, and unreachable DB all _page_. An expired mute pages too — that is what
  makes the 2026-08-29 `acsc` expiry work.

**Lesson worth keeping:** three correct PRs composed into a defect. Each passed
review in isolation; nothing reviewed the interaction. This is the
"operational review distinct from correctness review" rule in CLAUDE.md, and it
found nothing because no such review was run on the merged whole.

## 3. Axiom — checked, and thinner than expected

Queried directly via the API (`AXIOM_API_TOKEN` in `apps/web/.env.local`,
dataset `ask-arthur`), 72h window:

```
total events   458
  level=info   266
  level=null   173
  level=warn     5      ← all enforcement.*
```

**`warn` is the only tier that bypasses 10% INFO sampling** (see
`packages/utils/src/axiom-logger.ts` — sampling is per-_request_, hashed on
`requestId`, so a whole trace is kept or dropped together). Since nothing but
`enforcement.*` emits at warn, **most crons are invisible**, and GHA scraper
failures never reach Axiom at all.

**A trap, already walked into once:** `fn.start` (155) vs `fn.complete` (31)
looks like 80% of runs dying. It is not. By **distinct `requestId`** it is
**34 vs 31** — the per-step logging artifact. Always `dcount` the requestId
before concluding runs are being dropped.

**Not fixed here, deliberately.** The remedy — one warn-level `<fn>.summary` per
cron run — is a fleet-wide change across many functions and does not belong in a
PR about pager muting. Tracked in §5.

## 8. Traps added this session

- **A stacked PR does not auto-retarget when its parent merges.** GitHub only
  re-points it if the base branch is _deleted_, and the ship workflow prescribes
  `--delete-branch=false`. Merging then lands nothing on `main` and reports
  success. Fix with `git rebase --onto`, never a plain rebase — the parent was
  squash-merged, so a plain rebase replays content already in `main`.
- **A handoff's state claims go stale the moment the work lands.** The 08-02 doc
  shipped asserting "all eight green and unmerged" one commit after that stopped
  being true. Re-grep a handoff for its own assertions after acting on it.
- **`dcount` the requestId before believing a `fn.start`/`fn.complete` gap.**
- **Three correct PRs can compose into a defect.** Review the merged whole, not
  only each diff.
